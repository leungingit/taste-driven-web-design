## 9. 交付（阶段 9）

开始前：`gate.py check 9`。
- **按交付边界交付**：`design-and-implement` 的改版项目直接改现有源码，新建项目写到 constraints.yaml 的 `deliver_to`（如 `site/`、`public/`、`src/pages/`），不要默认写构建输出 `dist/`。`design-only` 的设计、原型和资产全部留在本期设计目录，`deliver_to` 只记后续实施目标，不能据此写入工程。
- **仅设计的文档同步是可选建议**：默认不修改项目文档，也不要求用户先决定文档同步才能完成交付。在最终交付说明最后给出建议，例如：「建议将本期设计系统的入口、适用范围和 UI 约束关联到项目文档，方便后续开发持续遵循。是否需要更新 `AGENTS.md` 和 `docs/design-system.md`？本次设计已交付，文档同步可另行安排。」不能把未答复当成同意。
- **用户同意后才同步**：新增阶段 9 的非视觉单选 `role=documentation-sync`，两个选项 ID 为 `update`（更新项目文档）和 `defer`（暂不更新）。用户明确答复后才发起这一步，记录其真实选择，不能代答。全部阶段已经通过后，即使原通道是 web，也可以用 `gate.py record ID --choice update --by user --via chat --quote "用户原话"` 登记真实同意；用户选择暂不更新时将 choice 改为 defer，无需重复确认。选择 update 后允许将本期 `work/handoff/DESIGN.md` 关联到项目根的 `docs/design-system.md`，并在 `AGENTS.md` 中写设计系统入口、适用范围和后续 UI 约束；只写关联与约束，不复制整份历史。门禁据此放行这两个文档，其他工程文件仍不可修改。落实后精确 ack，回顾保留这项独立决定。无需等待或主动创建此决策来阻塞原设计交付。
- `work/handoff/DESIGN.md`：主题、令牌表（三层）、字体、组件清单、图层表与动效规格、资产规范摘要；有设置项时附维度、预设、默认值、不变项和每个维度的 `who`。`target` 不是 web 时附**移植说明**：令牌与配置 JSON 的含义、哪些效果依赖浏览器能力、目标平台上的对应实现建议。
- `work/handoff/HANDOFF.md`：先写已确认的交付模式、决策 ID、原型入口、设计系统入口和验证结果。仅设计明确「当前工程尚未实施」，列出组件映射、实施顺序及后续工程验证；设计并实施列实际改动与工程验证。然后列**需要人工完成的步骤**，固定格式，每一步都写明验证方法：
  ```markdown
  ## 1. 替换线上的预置封面图
  - 目标位置：对象存储的封面目录（写明实际路径）
  - 文件：public/covers/*.png（写明数量）
  - 操作人：负责部署的同事
  - 验证：打开 /courses，14 张封面均为新版；抽查 3 张的 URL 返回 200
  ```
  涉及的外部系统（对象存储、CDN 缓存、后台配置、数据迁移、第三方账号）都要列出；没有则写"无"。
- **集中复核代定事项**：record/pending-review.md 非空时，建一个 `role: "pending-review"` 的 `multi` 决策，每条代定事项一个选项（能配图的配图），用户勾选"要推翻的"并在备注写新的决定。按结果修改后再验收。
- 保留 `.taste-design/` 全部历史；提交前核对 `git status` 的变更归属。仅设计新增变更只能是设计产物，另获文档同步确认后可包含 `AGENTS.md` 与 `docs/design-system.md`；设计并实施还包含已批准的实际源码。不能删除或提交用户原有改动来满足检查。

**闸门 9**：gate approve。
