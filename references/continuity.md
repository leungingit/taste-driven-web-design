# 上下文、当前工作记录与恢复

目标：即使没有先前聊天内容，也能从项目记录确定有效要求、当前工作位置、证据和下一步。项目记录负责恢复信息；能否唤醒已结束的回合，仍按 runtime.md 验证宿主能力。

## 记录分工

多期的记录边界：`record/state.json`、`scope.json`、`decisions/`、`progress.md` 都属于**当前期**；`.taste-design/project.json` 只负责期列表和父期/继承声明；`.taste-design/shared/` 只存跨期稳定的品牌与设计系统。恢复时先确认 `phase`，再读取当前期的记录，不把 P1 的进度套到 P2。

| 记录 | 职责 |
|---|---|
| `record/state.json`、`gate.py next --json` | 真实阶段、轨道、暂停或阻塞状态、未确认答案及下一步；由脚本维护 |
| `record/brief/` | 当前有效的范围说明、设计结论、内容和约束；相关条目附用户原话来源或决策 ID；不保存历轮实现日志 |
| `record/refs.yaml` | 素材的目标、反例、结构依据或当前实现职责及确认来源；制作前核对，不能混用 |
| `record/notes.md` | 对话补充及纠正的来源、状态、替代关系和落实位置；复用已有素材笔记，不覆盖原内容 |
| `record/progress.md` | 当前任务、已核对的进展、剩余工作、相关文件与验证；只保留接续所需内容 |
| 决策原文、`record/summary/`、历史样张 | 可回查证据；摘要用于定位，原始题目、答案和实际样张用于核对 |

不在工作记录里复制全部简报、阶段状态、答案或聊天历史。不用记录中的“已完成”替代检查实际产物，也不用摘要替代完整答案。历史结论保留在证据中，当前简报删除已被推翻的结论。

brief/traits 中的旧阶段细节和失败过程移入 `record/history/`，活文档只留当前结论、未决项及证据链接。回退时同步修正完成状态；不能一处写当前阶段 3，另一处仍把旧阶段 6 描述为当前已验收。归档不是删除历史，也不是把所有旧决定作废；仍有效的要求必须保留来源和适用范围。

## 对话补充及时落盘

用户新增限制、纠正理解、改变偏好或说明取舍原因时，在执行依赖它的工作前更新 `record/notes.md`；不等到阶段验收。普通状态询问无需记录。每项使用稳定编号，记录：

```text
编号：N001
来源：用户对话，2026-10-19；原话：“保留这张封面图，颜色可以调整。”
状态：用户已明确
适用范围：仅首页首屏
替代关系：无
落实位置：record/brief/constraints.yaml 的封面图约束；相关产物路径
```

- 状态区分“用户已明确”“待用户决定”“智能体暂定”“已被替代”。不把建议或推测写成用户要求。
- 更新要求时新增条目并引用旧编号；旧条目标明“已被 Nxxx 替代”，不静默抹掉来源或将新旧要求并列为有效约束。
- 同步相关简报、特征或约束；冲突尚未解决时保留待定标记，暂停依赖该结论的工作。影响已通过阶段时先按 workflow.md 的变更管理处理，不能靠修改笔记绕过回退与验收。
- 主要审美选择仍走决策协议；属于已有决策的对话作答仍用 `gate.py record --via chat --quote …` 登记。笔记不等于用户批准，也不自动确认答案。
- 来源只保存必要的原话或准确摘录，不复制无关聊天、凭证或私密配置。

## 当前工作记录的更新时机

新项目由 `gate.py init` 从 `templates/progress.md` 生成 `record/progress.md`。已有或迁移项目若缺失，或阶段不匹配、只有模板占位内容，先参考模板补建或纠正，再扩大调查。只核对当前状态、相关硬约束、素材职责、直接关联决定和产物；无法确认的项目写“待核对”，下一步写具体核对动作。不重新初始化，不猜测之前进展，不为补一份记录扫描所有历史。

在完成可验证的小步骤（例如一轮原型修改或一项检查）、进入等待、切换阶段、显式暂停或交接前更新。恢复后发现记录过时也要纠正。等待无变化时不反复改写，不记录每次工具调用。

记录对应阶段、关联决策 ID 和答案原始时间戳、相关源码或样张版本。分别写清：已完成哪些部分、剩余哪些部分、已执行验证及结果、未执行项、下一步具体动作。进入等待时写待答决策 ID；新答案到达后先读取完整内容再更新。

建议 progress 不超过 2000 字符，覆盖更新当前任务、有效结论与素材职责、关联答案版本、产物位置及一个可验证的下一步。全局约束和历史依据用链接；必要约束超过建议长度时保留并分节，不静默删减。每次重要事件及时保存，不依赖智能体一定能预知压缩时间或准确读取上下文剩余比例。

## 固定恢复顺序

每次启动、上下文压缩后或会话交接时执行：

1. 读取 SKILL.md 的全流程执行契约和本协议；已有可靠上下文时不重复加载。workflow、runtime、decisions 等只在实际动作涉及轨道变更、等待或建题时读相关小节，不把所有协议全文当成恢复前置条件。
2. 在项目根目录运行 `python3 $SKILL/scripts/gate.py context --json --compact`（多期项目加 `--phase ID`）。compact 输出只保留当前期、真实流程状态、checkpoint、继承文件是否缺失、空记录和分页入口，不交付或确认答案，不推进阶段。需要更多细节时再运行不带 `--compact` 的 `context --json`，或按 section 分页；不要每轮把完整 records、阻塞原文和全部产物模式重新载入。`records` 是定位入口，不是全部必读列表；`artifact_patterns` 指向产物或匹配模式，不要求展开全部版本。
3. 优先核对 progress、scope、全局硬约束及当前任务的素材职责，再定点读取简报相关章节、notes 中有效或待处理条目。`checkpoint.status` 为 missing/needs-review 时先按上节补建或纠正；available 只表示基本格式与阶段相符，不证明内容真实或最新。`exists: false` 表示缺失；未来阶段文档可缺，不能据此恢复旧阶段。
4. 只读 `stage_guides` 所列当前及并入阶段说明；仅核对当前任务的直接决定和产物。视觉恢复先查看有必要的目标参考、已选结果和当前实现，不扫描全部版本、动作帧或历史裁切。需要历史时通过 `history_index` 或明确 ID 定位原文，不遍历全部题目、答案或摘要卡。
5. **恢复结束条件**：能够指出当前任务、全局及任务有效约束与来源、待处理答案版本、直接相关产物、下一步及其完成条件，即结束恢复，执行一个小步骤。已读约 3–5 份相关项目记录后仍不能定位，应说明具体缺口并定点核对；不能继续以“再全面了解一下”为由扩大范围。必要的全局硬约束仍须读全，不能为了数量目标略过。
6. 随后运行 `gate.py next --json`（多期加 `--phase ID`），读取完整答案、核对已完成修改，落实剩余部分并精确 ack，再查询 next。若正在等待，核对实际地址和可作答项；当前对话尚未说明入口时先发通知再等待。记录含会话 ID 时先核查是否存活，不重复启动 waiter 或服务。

### 输出与读取预算

首轮恢复的项目记录与命令输出以约 8000–12000 字符文字为参考目标；已加载的技能规范不重复计入或重新读取。这不是模型的 token 上限或完整性保证。优先读取当前记录及直接依赖；工具输出过长时按文件章节或字段读取，不反复输出完整文件。默认不读取 skill 脚本实现；CLI 已给出状态和明确错误时先按协议处理，仅在具体的脚本缺陷需要排查时读取相关函数。避免递归列出素材、全量 git 状态、全部答案后再从中找当前任务。

### Token 预算的实际做法

- 第一次恢复用 compact；脚本测试或确有诊断需要时才用完整概览。完整概览是针对方言歧义的扩展，不是默认加载项。
- 读文件按职责拆开：先 `progress.md`，再 `scope.json` / `constraints.yaml`，然后只读当前阶段的 `brief.md` / `traits.md` 相关段落。历史问题用 ID + `summary/<ID>.md` 定位，再打开原题。
- 图片先看摘要卡缩略图或决策页的对比视图；只有需要判断纹理、细节或修复像素时才读原图。不要把整批原图一次性放回上下文。
- 命令输出只留决定性证据：测试失败保留失败测试名和 traceback 首段，日志保留错误与关键上下文，避免重复输出同一份长 JSON。
- `progress.md` 保持约 2000 字符以内；超过时把历史依据改为链接或 ID，并删除已被替代的结论。不要把工作记录当聊天日志。
- 多期项目按期隔离上下文：处理 P2 时只读 P2 的 `record/`、`progress.md` 和 `shared/` 中明确继承的路径；P1 只按需要查具体决策或交付，不默认重读。

`checkpoint.text` 和默认阻塞示例可能是预览，`truncated: true` 表示尚有内容；索引的 `pagination` 提供总数和下一页偏移。不能将其当作完整要求或已落实凭据。只有当前任务需要时查详情，例如：

```bash
python3 "$SKILL/scripts/gate.py" context --json --section decisions --offset 5
python3 "$SKILL/scripts/gate.py" context --json --section blockers --offset 0 --limit 5
```

可查询 decisions、unacked、blockers、open、queued、inherited；详情每页默认 5 项，`--limit` 为 1–20。继承清单在概览中也只显示首屏，按 `pagination.inherited.next_offset` 续读才能核全本期继承。分页只读，不创建运行目录，不自动消费答案。默认概览不展开历史全文；详情中的路径、ID 和阻塞原文保持完整。若单项很长，定点核对来源，不再重复输出其他项。待落实答案仍用 `next --json` 的 `new` 完整交付，JSON 中省略重复的 `new_text` 摘要，不能截掉备注、数值或设置要求以节省上下文。必要内容超过预算时明确剩余范围并分批读取，不静默省略。

恢复已达到终点仍发现规范、范围、已批准关系相互冲突时，把冲突写进 progress，按变更管理处理；不靠反复阅读脚本解决授权或适用范围问题。宿主压缩模型输入超限属于另一条故障链路；记录实际错误与已保存的接续入口，不能承诺 skill 能更改宿主上限，也不能反复加载全历史后再重试压缩。

`context` 的输出是查询时快照，之后用户仍可提交新答案。`unacked` 仅为定位索引，不能凭它直接 ack；用 `next` 读取完整答案和当前版本。答案只落实一部分时保持未确认，先检查已做修改，补齐剩余内容后再确认。

记录不一致时分别核对：阶段和轨道以状态机为准；答案以当前原文及版本为准；要求核对来源、替代关系和既有批准范围；进展以实际产物为准。较新的笔记不自动取得回退或验收授权。仍无法消除的歧义向用户澄清，其余不受影响的工作可以继续。

## 恢复验证

脚本回归应使用独立命令行进程，只提供项目根目录，验证：

- 当前工作记录过时，也不会覆盖真实阶段或推进流程。
- 只落实部分的答案在恢复后仍待确认，完整备注、数值和版本可重新读取。
- 旧版本确认不吞掉新答案；完成剩余工作后才能按实际版本确认。
- 缺失工作记录可被定位；合并阶段的说明和决策均可找到；历史全文不混入恢复索引。
- 历史和当前阶段决策增长后，默认输出仍有界，全部详情可分页找到；长预览显式标记，不改变完整答案及版本确认语义。
- 缺失、占位或阶段不匹配的 progress 提示优先补建；available 也不能推进状态。布局自由度改变后旧检查报告不能继续作为验收依据。

脚本通过后，还需在真实设计项目的副本上做一次独立会话人工验证：仅提供项目路径和本协议入口，不提供原聊天，让智能体报告当前任务、有效要求来源、已完成与未完成项及下一步；与原会话记录和实际产物对照。加入一条新要求替代旧要求、一个只落实一半的答案，检查是否正确恢复且不重复执行。分别覆盖有 progress 和缺失 progress，记录首次可执行动作前的读取文件数、文字输出量和图片数，确认不再全历史扫描。未进行这项验证时如实标注“独立会话语义恢复未验证”；脚本测试不能证明模型一定正确理解全部要求。
